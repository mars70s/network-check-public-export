# Test Specification

## 文書の目的

この文書は、Network Checkの公開機能を公開前に確認するための受け入れ確認仕様です。公開されているDNS、TLS、HTTP、メール関連レコードなどを読み取り専用で確認し、結果表示、安全境界、データ保存方針が公開文書と整合していることを確認します。

この文書は、脆弱性診断手順や侵入試験手順を定めるものではありません。攻撃手順や具体的な回避方法ではなく、公開サービスとして期待される品質と安全境界の確認観点を整理するものです。

本文書は公開前の受け入れ確認仕様であり、記載項目のすべてが自動テストとして実装されているとは限りません。自動テストとして実装されている範囲は`tests/`を参照してください。

## 公開リポジトリにおけるテスト対象範囲

本仕様書のテスト対象範囲は、公開リポジトリに含まれる通常の利用者向け機能と公開説明ページです。

- Client Informationの表示
- Domain、DNS Timing、IPv4 / IPv6 Preference
- TLS、HTTP/2、Security Headers
- MX、SPF、DMARC
- PTR、CAA
- Domain Multi Check
- 公開説明ページ、privacy、terms、contact
- 入力値エラー時の表示
- 公開向けの接続先検証
- 匿名利用集計として保存する情報の範囲

## 対象外範囲

次の項目は、この公開用テスト仕様の対象外です。

- ソースコードやテストコードの内部設計レビュー
- デプロイ、サーバ、DNS、Nginx、systemdなどの運用設定
- 実行環境名、内部URL、内部運用手順
- 秘密情報、認証情報、鍵、ログ、データベースなどの実行時データ
- 不正利用対応の詳細や運用しきい値
- 脆弱性スキャン、侵入試験、認証試行、負荷試験

## 公開機能ごとの確認観点

### DNS確認

Domain、DNS Timing、IPv4 / IPv6 Preference、PTR、CAAでは、入力に応じた公開DNS情報が表示されることを確認します。

- 有効なドメインまたはIPアドレスに対して、期待される種類のDNS結果が表示されること。
- レコードが存在しない場合や問い合わせに失敗した場合に、利用者が状態を理解できる表示であること。
- DNS問い合わせ時間は参考値として表示され、性能全体を保証するものではないこと。
- 対象側の設定変更やポートへの接続を行うと誤解される記述がないこと。

### HTTP確認

TLS、HTTP/2、Security Headersでは、公開HTTP / HTTPS対象に対する通常の確認結果が表示されることを確認します。

- TLSでは、標準ポート443への通常接続で取得できるTLSバージョン、暗号方式、証明書情報が表示されること。
- HTTP/2では、HTTPバージョンとHTTPステータスが表示されること。
- HTTP/2確認はリダイレクトを自動追跡せず、クロールや性能測定を行うものではないこと。
- Security Headersでは、選択したレスポンスヘッダーの有無と値が表示されること。
- ヘッダーの有無だけでWebサイト全体の安全性を保証すると誤解される記述がないこと。

### MX / SPF / DMARCなどメール関連レコード確認

MX、SPF、DMARCでは、公開DNSに登録されているメール関連情報の表示を確認します。

- MXレコードの有無と値が表示されること。
- SPFとDMARCの公開DNSレコードが表示されること。
- レコードがない場合に、診断対象ごとの結果として分かりやすく表示されること。
- SMTP接続、認証試行、メール送信、実際のメール認証を行うと誤解される記述がないこと。

### Domain Multi Check

Domain Multi Checkでは、ドメインを入力にする複数の確認項目をまとめて実行できることを確認します。

- 選択した確認項目だけが実行対象になること。
- 各結果に個別機能と同じ入力境界と限界が適用されること。
- PTRやSecurity Headersなど、入力形式が異なる機能はDomain Multi Checkに含まれないこと。
- 一部の確認が失敗しても、他の確認結果を読み取れる表示であること。

### 入力値エラー時の表示

入力値が不足している場合、形式が不正な場合、公開確認対象として扱えない場合の表示を確認します。

- 利用者が修正すべき入力内容を理解できること。
- 内部例外、スタックトレース、内部パス、秘密情報が表示されないこと。
- ドメイン、IPアドレス、URLの入力形式ごとの境界が公開文書と整合していること。
- エラー表示に、攻撃手法へ寄りすぎた説明が含まれないこと。

### 安全な接続先検証

外部ネットワーク確認の前に、公開確認対象として扱える接続先かを検証することを確認します。

- ループバック、プライベート、リンクローカル、マルチキャスト、予約済み、その他の非公開または通常の公開確認対象として扱うべきではない接続先を拒否、または回避すること。
- 埋め込み認証情報を含むURLや、許可されていないポートを受け付けないこと。
- リダイレクトによって検証済みの接続先境界が変わる可能性がある確認処理では、リダイレクト追跡を制限すること。
- 確認観点は一般的な安全境界にとどめ、具体的な突破手法や攻撃ペイロード集を文書化しないこと。

### データ保存方針

Data Handlingの説明と実際の保存方針が整合していることを確認します。

- 通常の診断結果はリクエストごとに生成され、入力対象ごとの診断履歴として保存されないこと。
- 匿名利用集計は、日ごとの利用回数や選択項目の件数把握を目的としていること。
- 利用者が入力したドメイン、IPアドレス、URLを匿名利用集計レコードの保存対象にしないこと。
- HTTPヘッダー、Cookie、セッション、リクエスト本文、秘密情報、認証情報、認可ヘッダー、個別の診断結果を匿名利用集計レコードへ保存しないこと。

## 受け入れ条件

公開前の受け入れ条件は次のとおりです。

- 公開機能の主要な正常系結果が、READMEとChecksの説明に沿って表示されること。
- 入力値エラー時に、利用者向けの自然なエラー表示になること。
- 公開確認対象として扱うべきではない接続先が拒否、または回避されること。
- 結果表示が対象全体の安全性や正常性を保証するものではないこと。
- 内部運用情報、秘密情報、実行時データ、ログが公開画面や公開文書に含まれないこと。
- データ保存方針がData Handlingの説明と整合していること。

## 公開前確認チェックリスト

- README、Security Policy、Data Handling、Checksの説明と公開画面の表示が整合している。
- 新規または変更した公開文書に、内部運用情報や秘密情報が含まれていない。
- Markdownに未閉じのコードフェンス、HTMLコメント、HTMLタグ、Jinjaブロック、競合マーカーがない。
- 公開機能の入力、正常結果、エラー表示、安全境界が確認されている。
- 実行時処理、サーバ、デプロイ、ソースコードの変更を含まない文書変更である。

## セキュリティ境界確認

Network Checkは、公開されている通常のネットワーク情報を確認するための読み取り専用サービスです。受け入れ確認では、次の境界を維持していることを確認します。

- 対象システムの設定、データ、稼働状態を変更しない。
- ポートスキャン、脆弱性診断、侵入試験、認証情報の試行、メール送信、大規模なクロールを行わない。
- 公開HTTP / HTTPS URL以外や、公開確認対象として扱うべきではない接続先を受け付けない。
- リダイレクト追跡を制限し、利用者が指定した公開対象とは異なるネットワーク位置へ到達しないようにする。
- 公開文書では一般的な安全境界を説明し、内部運用の詳細を公開しない。
